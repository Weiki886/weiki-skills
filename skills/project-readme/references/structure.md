# README 结构与章节规则

## 阅读流

按此顺序选章节，删掉没有证据支撑的：

```
头部区块：Logo / 项目名 / 一句话定位 / badge / 语言切换 / 锚点导航
→ 能力总览段：命令或工具、输入输出、默认安全姿态
→ Quick Start（必须；1～3 步给出可验证结果）
→ 特性：用户结果 + 实现机制证据
→ 安装与前置条件（详细方式、版本与路径）
→ 任务化用法 / 核心工具或 API
→ 配置（环境变量、宿主、数据目录等，按实际）
→ 为什么需要它 / 原理与设计取舍
→ 安全边界 / 隐私与数据流向
→ 错误码 / 排错
→ 已知限制
→ 开发
→ 设计文档链接
→ 贡献（仅当有实际贡献流程）
→ 社区（仅当有实际渠道）
→ License
```

四条顺序约束：

1. 读者理解「这是什么」之前，不该被要求配置。
2. 读者进入完整特性或原理之前，应该已经看到最短运行路径和验证方法。
3. **原理、背景、设计取舍放在读者已经跑通之后**。它们建立可信度，但不该挡在第一屏——先让人看到东西能用，再解释为什么这么设计。
4. 有读写本地数据、凭据、网络请求或模型调用时，让读者在执行风险操作前能跳到安全边界；Quick Start 里不要隐藏这些代价。

## 按项目类型取舍章节

类型决定读者期待。删掉该类型不需要的章节，而不是留空。

### CLI 工具

读者想知道「装了能干什么」。

| 该有 | 该省 |
| --- | --- |
| 一句话定位 | 架构图（除非多组件协作） |
| Quick Start + 验证命令 | 完整选项表 |
| 按任务组织的命令 + 真实输出 | API 文档 |
| 安装前置条件、版本与路径 | 源码目录结构 |
| 配置（配置文件 / 环境变量） | 内部实现细节 |
| 读写边界、确认/备份/只读默认值 | 凑数 badge |
| 排错与已知限制 | 贡献指南（solo 项目） |

### MCP / 本地开发者服务

读者想知道「怎么注册、工具会暴露什么能力、数据会不会离开机器」。

| 该有 | 该省 |
| --- | --- |
| 一句话定位 + 能力总览段 | MCP 泛泛科普 |
| 包名准确、版本策略与发布文档一致的 Quick Start | 未验证的 `npx <name>` |
| 已验证宿主的配置片段 | 所有宿主的想象配置 |
| 服务发现/连接验证方法 | 完整 JSON Schema 搬运 |
| 工具名、参数、授权与失败行为 | 内部实现细节 |
| 凭据存放与环境变量配置 | 真实密钥或 `.env` 示例 |
| 隐私与数据流向 | 「绝对安全」类承诺 |
| 错误码、排错、平台限制 | 与项目无关的模型推荐 |

### 库 / SDK

读者想知道「能帮我解决什么问题」。

| 该有 | 该省 |
| --- | --- |
| 一句话定位 | 完整 API 引用（链接到 docs/） |
| 安装（包管理器） | 长篇教程 |
| 最小可跑示例（5~10 行） | 内部实现细节 |
| 核心概念 / 主要类型 | 社区（无实际渠道时） |
| 兼容性（语言 / 运行时版本） | 路线图（未确认时） |

### 应用 / 产品

读者想先看到东西。

| 该有 | 该省 |
| --- | --- |
| 截图 / GIF（放最前） | 源码目录结构 |
| 一句话定位 + 差异点 | 代码级 API 文档 |
| 安装 / 获取方式 | 开发者文档（链接出去） |
| 首次使用步骤 | 内部实现 |
| 主要功能 | 贡献指南（非开源时） |

### 研究仓库

读者想知道「结果可信吗、能复现吗」。

| 该有 | 该省 |
| --- | --- |
| 论文 / 预印本链接 | API 文档 |
| 核心结果（benchmark / 指标） | 教程 |
| 复现步骤（数据 + 环境 + 命令） | 长期维护承诺 |
| 依赖与环境版本 | 路线图 |
| 已知限制与适用边界 | 社区（无实际渠道时） |

### Agent Skill 仓库

读者想知道「怎么装、在哪个 agent 上能用」。

| 该有 | 该省 |
| --- | --- |
| 一句话定位 | 架构图 |
| skill 列表与各自用途 | 完整 API 引用 |
| 安装方式（脚本 / clone + cp） | 内部实现 |
| 兼容的 agent（Codex / Claude Code / Cursor 等） | 社区（无实际渠道时） |
| 目录结构 | 路线图（未确认时） |

### Monorepo

| 该有 | 该省 |
| --- | --- |
| 一句话定位 + 包含哪些包 | 每个子包的完整文档 |
| 各子包一句话说明 + 链接 | 子包 API 细节 |
| 统一的开发 / 构建入口 | 逐包安装说明（放子包 README） |

## 各章节写法

### 一句话定位

说清三件事：是什么、为谁 / 解决什么处境、一个事实性差异点。

避免无法验证的最高级（「最快」「最好」「业界领先」「生产就绪」），用具体事实替代。

反例与修正：

| 差 | 好 |
| --- | --- |
| `一个强大的现代化 CLI 工具集` | `切换 Provider 后修复 Codex 历史会话丢失的 CLI，纯标准库，Python 3.9+` |
| `业界领先的 AI Skill 集合` | `个人维护的 Agent Skills，覆盖代码实现、审查、写作与 GitHub 交付流程` |

### 视觉演示

视觉素材按信息增量选择，不是所有 public 项目的必填项。优先级：

| 形式 | 适用 | 工具 |
| --- | --- | --- |
| GIF / asciinema | CLI、TUI、交互式工具 | `asciinema rec`、`vhs`、`terminalizer` |
| 截图 | GUI、Web 应用、可视化输出 | 系统截图 |
| 真实终端输出代码块 | 无录制条件时的兜底 | 直接粘贴真实输出 |

规则：

- 演示要展示**最有代表性的一个场景**，不是全部功能的巡礼；CLI/MCP 如果最短命令和真实输出已经足够清楚，可以不做 GIF。
- 输出必须真实。不手工美化、不编造行数与耗时。
- 没有素材时用真实终端输出兜底；不要为了凑首屏制造无信息量的 logo 动画或界面巡礼。
- 素材放仓库内（`assets/`、`docs/`），不外链到会失效的图床。

### 头部区块

对外开发者工具可使用克制的居中头部，但正文不要整体居中：

- Logo：只有仓库内已有可信素材时使用，写明宽度与 `alt`。
- 项目名：使用实际包名或产品名，不临时改名。
- 定位：1～2 句，说明做什么、为谁、关键事实差异。
- badge：只放 License、CI、包版本、运行时版本等能验证的 badge。
- 语言切换：只有对应语言 README 真实存在时才放。
- 导航：README 超过约 100 行时放一行，用 ` · ` 连接主要章节。

### 能力总览段

头部之后用一段具体话说清：

- 暴露哪些命令、工具或主要入口；
- 输入从哪里来、输出写到哪里；
- 默认是否只读、失败即关闭、需要确认、预览或备份；
- 与相邻工具或项目的关键差别。

不要写成「一个强大、安全、高效的解决方案」。如果项目处理本地数据库、文件、剪贴板、MCP 宿主或模型请求，这一段就要让读者立即知道风险面。

### 特性

3～8 条即可，每条采用「用户结果 —— 实现机制/证据」：

```markdown
- **只读优先** —— 导出走 `mode=ro` 与 `PRAGMA query_only = ON`；只有写入命令会修改数据。
```

安全、默认值、备份、失败处理、兼容策略可以成为特性，但必须能在源码、测试或配置中核实。不要把功能清单全部包装成亮点。

### 锚点导航

README 超过约 100 行时加一行导航，让读者跳转而不是滚动：

```markdown
[安装](#安装) · [快速开始](#快速开始) · [用法](#用法) · [原理](#原理) · [限制](#已知限制)
```

### Quick Start

必须给出从安装完成到「第一个有用结果」的最短路径，三段齐全：

1. 运行命令（真实入口、真实参数）
2. 预期输出（真实输出片段或截图）
3. 一句话说明这个结果意味着什么

优先控制在 1～3 步；需要复杂宿主或模型配置时，Quick Start 可以只走到服务注册/发现，再链接到详细配置章节。命令必须在仓库里能找到对应入口，找不到就问用户，不推测参数名。

### 安装

给真实存在的路径：包管理器、安装脚本、或源码构建。多平台时分别列出，不写「按需安装」。

未发布到包管理器时，不要写 `pip install <name>` / `npm i <name>` 这类看起来标准但实际不存在的命令。

安装章节应列清运行时版本、系统前提、外部账号/服务、写入目录和必要权限。包名有 scope 或固定版本要求时，Quick Start 与安装章节保持完全一致；不要为了简短丢掉关键版本。

### 用法：按任务组织

README 回答「我想做什么」，`--help` 回答「有哪些参数」。两者分工不要混。

正确形式——每个任务一句说明加一条命令：

~~~markdown
列出当前可见的对话

```bash
cskit export --list
```

导出指定会话到桌面

```bash
cskit export 2BLOG --output ~/Desktop/CodexExports
```
~~~

错误形式——把 `--help` 的输出搬进 README：

```markdown
| 选项 | 作用 |
| --- | --- |
| `--list` | 只列出未归档对话 |
| `--output` / `-o` | 输出目录 |
| `--codex-bin` | Codex 可执行文件路径 |
| ...（还有 5 行）
```

参数表的问题：它复刻了 `--help` 已经提供的信息，占据首屏后的黄金位置，却不告诉读者任何「什么时候该用」。

例外：某个参数有非显然的行为或坑（默认值反直觉、有破坏性、与其他参数冲突），单独用一段讲清，而不是列进大表。

### MCP 宿主与工具配置

MCP 项目按宿主写配置，例如 Claude Code、Codex 或其他已验证客户端：

- 配置片段中的 `command`、`args`、server 名称、环境变量必须来自包入口、文档或真实运行。
- 密钥不要写进项目级配置示例；优先展示 Keychain、交互登录或占位符环境变量。
- 每个宿主片段后给服务发现验证方式，例如 `/mcp`、`codex mcp list` 或该宿主的真实等价命令。
- 工具说明聚焦名称、参数含义、授权副作用、返回与失败行为；完整 schema 链接到 `docs/`。
- 环境变量表适合配置面较广的项目，列出默认值、是否必需、用途和合法值；简单项目不要硬凑大表。

### 原理与设计取舍

放在用法之后。这一节的价值是建立可信度：证明作者真的踩过坑、理解问题本质。

写法：先说读者会遇到的现象（报错信息、异常表现），再说原因，最后说这个项目为什么这样设计。

不要放在第一屏——读者还没跑起来就读设计文档，会直接关掉。

### 安全边界、隐私与数据流向

只要项目触及本地文件、数据库、剪贴板、凭据、网络、Provider 或模型调用，就应说明风险边界。public 或对外分发项目优先用表；solo 项目可压缩成一段，但不能跳过会影响用户数据或安全的事实：

| 能力/命令 | 读取 | 写入 | 网络/外部服务 |
| --- | --- | --- | --- |

还应按证据说明：默认权限、路径校验、符号链接处理、临时文件清理、脱敏日志、dry-run、确认、备份、回滚、失败即关闭策略，以及哪些数据会离开本机。

写「只读」「不收集数据」「不会上传」之前，必须在源码、测试或配置中找到依据。Provider 或第三方服务的数据保留、训练与管辖策略不能由项目代其承诺。

### 错误码与排错

面向程序集成的项目可提供错误码表，按输入/权限/资源/Provider/输出等类别分组，并标明是否可重试。

排错条目采用「症状 → 原因 → 动作」：

```markdown
- **`PATH_NOT_ALLOWED`：** 文件不在允许根目录内。传入已规范化的绝对路径，或把其父目录加入允许列表。
```

只写代码中真实存在或用户可稳定复现的错误；不要把「重启」「重新安装」当作万能建议。

### 已知限制

solo 项目也要写。内容包括：不支持的场景、已知 bug、平台限制、依赖前提。

这一节是可信度来源之一——承认边界比假装万能更容易被信任。

### 架构图

可选，仅当组件、边界、关系都能从代码验证时才画。ASCII 或 Mermaid 都可以，按仓库既有习惯与读者选择，不强制某一种。

不画仓库里不存在的组件，不画推测的调用关系。宁可整节省略，也不画一个「看起来很专业」的假图。

### 亮点表

3～8 条。每条前半是读者能获得的结果，后半是仓库里的事实依据。

不要把完整功能清单伪装成亮点表。

### Badge

仅当对应资源真实存在且 URL 稳定时才加：License、CI 状态、包版本、下载量。

不猜 badge 端点。CI badge 要对应真实存在的 workflow 文件。solo 项目通常一个 License badge 就够，不需要凑一排。

### 深度文档链接

按「读者想做什么」组织，不按文件名罗列。

```
- 想快速上手 → docs/getting-started.md
- 想了解配置项 → docs/configuration.md
- 想参与开发 → CONTRIBUTING.md
```

设计文档可按提案、ADR、规范、安全、测试、发布分组。链接必须存在；不要把 `docs/` 里所有文件机械倒上首页。

### 开发

给贡献者真实的安装、测试、构建/检查命令，并说明测试覆盖了什么关键风险。命令要能从干净环境运行；若需要系统依赖、密钥或特定平台，明确写出。
