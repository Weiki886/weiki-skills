# 项目 README 规范

README 不是参数手册，也不是宣传页，而是让陌生人信任项目并跑出第一个结果的最短路径。

目标不是把章节填满，而是让读者三件事都成立：**知道这是什么**、**知道是否适合自己**、**能跑出第一个结果并理解风险边界**。

## 核心原则

1. 每一条声明都要有证据。仓库里验证不了、用户没确认的，一律不写——不是写得含糊，是不写。
2. Quick Start 不可省：必须给出从安装到「第一个有用结果」的最短路径，且命令真实存在。验证不了就问用户，不留空、不编。
3. 已有 README 先问处理方式（替换 / 保留部分 / 就地扩展），不猜、不擅自覆盖用户手写的内容。
4. 首屏给定位和入口：public 项目用项目名/Logo、一句话定位、真实 badge 与导航建立第一印象，紧接着给 Quick Start；GIF/截图只在比文字更能说明价值时使用。
5. 展示优于陈述：终端输出、截图、代码、真实数字，胜过任何形容词。
6. 按任务组织，不按参数罗列：README 讲「想做什么 → 用哪条命令」；完整参数表交给 `--help`，不搬进 README。
7. 一行不帮读者「判断、信任或行动」，就删掉。
8. 触及本地文件、数据库、凭据、网络或模型调用时，必须写清安全边界：读什么、写什么、什么会离开本机、默认是否只读/确认/备份/失败即关闭；没有代码证据不写安全承诺。
9. README 只放门面，深度内容链接到 `docs/`、`CONTRIBUTING.md`，不把手册塞进首页。
10. 匹配项目，不套模板：CLI、MCP、库、应用、研究仓库的最佳 README 不是同一个东西。
11. 不写「业界领先」「生产就绪」「极致性能」这类无法验证的自夸（红线见 `content-writing`）。

## 先定场景

先判断这个 README 的读者是谁，据此决定详细程度：

- **solo（个人项目 / 内部工具 / 自用脚本）**：读者主要是你自己和未来的你。必写：一句话定位、Quick Start、已知限制。可省：badge、贡献指南、社区渠道、Star History、路线图。底线是三个月后你自己还能照着跑起来。
- **public（开源 / 对外分发 / 团队共享）**：读者是陌生人。完整结构：定位、价值、Quick Start、用法、配置、文档索引、贡献、License；badge 与社区信息按实际存在情况补。

缺省判定：仓库公开、发布到包管理器、或有外部使用者 → public；私有自用、一次性 → solo。混合场景按 public 写，不向下放松。

## 先定模式

同样先判断「这次要做什么」，不同模式的第一步完全不同：

| 模式 | 何时用 | 第一步 |
| --- | --- | --- |
| **create** | 没有 README，或用户明确要求重写 | 扫仓库收集事实 |
| **improve** | 有 README，要补强或重构 | 先读现有 README，问处理方式，再动 |
| **audit** | 只要诊断，不改文件 | 逐条核对 README 声明与仓库实际状态，出问题清单 |

**关键门禁**：发现已有 README 时，停下来让用户选处理方式——① 完全替换 ② 保留指定内容后重写 ③ 就地扩展。不从「帮我写个 README」推断成 ①。

## 首屏与开发者工具风格（public 项目）

读者用一屏决定去留，所以第一屏只做一件事：**让他看到这东西在干什么**。

面向 CLI、MCP、本地开发者工具时，优先采用克制、可验证的开发者文档风格：

```
<div align="center">
  可选 Logo
  # 项目名
  **一句话定位**
  badge（真实存在的才放）
  语言切换（确实有对应 README 时）
  锚点导航（文档超过 100 行时）
</div>
---
能力总览段：具体列出命令/工具、输入输出与默认安全姿态
```

三条规则：

- **一句话定位要短到能记住**。一行左右讲清「是什么、为谁、最关键的事实差异」，把原理留给后面。
- **能力总览要具体**。直接列出真实命令或工具、输入输出、读写对象与默认安全姿态；不要只写「高效、安全、智能」。
- **Quick Start 紧随其后**。优先给 1～3 步最短路径，最后一步必须能验证安装或服务发现；复杂配置再放到后面的安装/配置章节。

视觉素材不是必填项：GIF / asciinema、截图、真实终端输出按信息增量选择。没有素材时，不必为了凑首屏编造演示；应把真实命令、预期输出和验证方法写清楚。

solo 项目可以跳过 Logo、badge、导航，但「一句话定位 + 能看到输出」仍然值得保留。

## 证据阶梯

写每一条内容前，先确认它站在哪一级：

| 级别 | 来源 | 怎么用 |
| --- | --- | --- |
| 1 | **仓库原生**：源码、测试、示例、配置、CI、Tag、已有截图 | 直接写 |
| 2 | **用户确认**：定位、差异化、指标、截图、案例 | 直接写 |
| 3 | **外部可验证**：包管理器页面、Release、公开 benchmark | 写，并给出链接 |
| 4 | **无来源** | 不写。重要就问用户，不重要就删 |

禁止编造：安装命令、CLI 参数、API 签名、配置项、环境变量、路径、性能数字、兼容性承诺、License 条款、社区链接、依赖版本。

细则与自查见 `references/evidence.md`。

## 主流程

1. **定场景与模式**：solo / public，create / improve / audit。有已有 README 就先问处理方式。
2. **扫仓库收事实**：包元数据、入口点、目录结构、配置面、已有文档、Git/CI、可用素材，以及读写路径、凭据、网络、模型调用、错误码等风险面。这一步只收事实，不做判断（清单见 `references/evidence.md`）。
3. **判断项目类型与读者**：CLI / MCP / 库 / 应用 / 研究 / Agent Skill / Monorepo——类型决定该写哪些章节（见 `references/structure.md`）。
4. **验证 Quick Start**：找出「装好之后第一条能跑出结果的命令」，并实际确认它存在。找不到就问用户，这一步不通过不往下走。
5. **列章节计划**：按项目类型选章节，明确每节的证据来源；无证据支撑的章节直接不列。同时定首屏方案、Quick Start 验证方式，以及是否需要安全/数据流向、错误码和排错章节。
6. **写初稿**：首屏与能力总览 → Quick Start → 特性 → 安装/配置 → 按任务组织的用法 → 为什么需要它（原理 / 背景）→ 安全/隐私边界 → 错误码/排错 → 已知限制 → 开发与深度文档。原理和设计取舍放在读者已经跑通之后，不放前面。
7. **过质量门禁**：对照 `references/checklist.md` 逐条自查，尤其是事实与可执行性。
8. **交付**：默认在对话里给草稿；用户明确说写入才落盘。写入前再过一遍门禁。

## 输出要求

完成后简洁给出：① 判定的场景与模式；② 项目类型与目标读者；③ 章节计划及每节证据来源；④ README 草稿；⑤ 需要用户确认或补充的清单（哪些声明缺证据）；⑥ 已知未覆盖项。

不得把「猜的」写成「验证过的」。缺证据的地方要显式列出来，不要用模糊措辞蒙过去。

## 红旗

- Quick Start 缺失、留空，或命令是编的（仓库里根本没有那个入口）。
- 发现已有 README 却直接覆盖，没问用户处理方式。
- 未经确认就写性能数字、兼容性范围、用户量、star 目标。
- badge 指向不存在的 CI、包或 License。
- 章节按模板填满，出现空标题或「TODO」「敬请期待」。
- 把完整 API 手册塞进 README，而不是链接出去。
- 用大段选项表复刻 `--help` 的输出，而不是按任务给命令。
- 首屏只有口号或原理，没有真实入口、命令/工具清单或可验证结果。
- 工具会读写本地数据、接触凭据、发网络请求或调用模型，却没有安全/数据流向说明。
- 写了「只读」「不泄露」「失败即关闭」「零配置」等安全或易用承诺，但代码、测试或配置里没有证据。
- 排错只写「重启试试」，没有具体症状、错误码、原因和处理动作。
- 一句话定位写成一整段；或先讲原理背景，把「怎么跑起来」压到很后面。
- 形容词堆砌：「强大」「优雅」「极致」「开箱即用」占据了本该放证据的位置。
- solo 项目硬套开源模板，写贡献指南、行为准则、社区渠道，但这些都不存在。
- 架构图里画着仓库中并不存在的组件或调用关系。
- 未经用户同意就写入文件。
