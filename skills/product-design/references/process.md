# 过程细则与样例

## 调研清单

行业与竞品调研回答五个问题：

1. 这个问题在行业中的通行做法是什么？
2. 有哪些相关竞品 / 开源项目，各自怎么取舍？
3. 各方做法的优劣分别是什么？
4. 哪些可借鉴、哪些应规避？
5. 我们的场景与它们的差异在哪里——为什么不能照抄？

要求：

- 结论附来源（官方文档链接、源码或真实使用证据）；没有来源的标 `TBD`。
- 不编造竞品能力、版本行为或市场结论。
- 产出载体自定（协作文档、Wiki 皆可），组内有共识即可，不强制写入 Issue。

## 写回理解格式

调研与动笔前发给用户确认：

```text
我的理解：
- 要解决的问题：...
- 目标用户：...
- 成功的样子：...

用户明确说的：...
我的假设：...
待确认（TBD）：...
```

收到纠正后更新理解再往下走；已给出充分目的与约束时，直接复述确认，不重复追问。

## 原型随阶段

- **尚无基础代码（项目早期）**：原型可用原型工具独立完成，在哪里跑都一样，本地跑通即可。
- **已有真实工程代码**：原型建立在真实代码之上，以「只用于展示、不合并的 PR」承载（本质是 web coding）。核心目的是把「产品要做成什么样、要达到什么行为」定义清楚；不在早期那份未合并原型上继续堆功能，避免与线上逻辑脱节。
- 原型图 / 设计链接直接贴在产品设计文字稿之下，不单独为 UI 设计建 Issue。

## 草案 PR 评审

设计文档与原型的逐行评审可借助不合并的草案 PR 进行：

1. 把设计稿作为文件提交到草案 PR，评审者在行内评论；
2. 讨论收敛后把定稿落回 Issue，关闭草案 PR（不合并）；
3. Issue 打上对应状态与粒度标签，此后文档只读，变更另写新版。

## 真实样例

无界面产品（纯文字决策，无原型）：

- [goplus/xgo#2797 Function Decorators](https://github.com/goplus/xgo/issues/2797)：语法层面的文字提案。

有界面产品（文字定稿 + 原型）：

- [goplus/builder#494 v1.3 UI Design](https://github.com/goplus/builder/issues/494)
- [goplus/builder#3214 animation UI](https://github.com/goplus/builder/issues/3214)

状态流转：

- [goplus/xgo#2802 Flat Mode](https://github.com/goplus/xgo/issues/2802)：被接受并标记 `FullSpec`。
- [goplus/xgo#2667 defer 命令语法](https://github.com/goplus/xgo/issues/2667)：被拒并记录理由——被拒绝是正常结果，不是失败。
