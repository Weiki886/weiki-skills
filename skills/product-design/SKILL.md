# 产品设计规范

软件的价值取决于是否「做对的东西」，而不只是「把东西做出来」。产品设计的任务是在开发投入前明确「做什么、为谁做、解决什么问题、不做什么」，并在团队内达成一致——方向错了，实现得再好也没有价值，且发现越晚、返工越贵。

产品设计的产出是工程文档：定稿后只读，需求调整另写一份描述变化，不覆盖旧文档。

## 核心原则

1. **决策三要素**：每个设计点回答「有哪几种做法、选择哪一种、为什么」，并明确本期不做什么。只罗列功能、不呈现取舍的文档，不属于合格的产品设计。
2. **一次一个增量**：一份 Proposal 只确定一个清晰的设计点，相邻决策拆给后续提案。窄而可被通过、实现、验证的提案，优于试图解决全部未来问题的大提案。
3. **简单直接**：一个真实例子能说明的，先给例子、再作抽象；一条规则能表达的行为，不引入多套机制。
4. **减法设计**：主动移除冗余与非必要负担（样板代码、手动步骤、需用户额外记忆的特例），不为求「完整」堆砌功能。
5. **边界清晰**：写明解决什么、不解决什么、哪些属于合法情况、哪些属于错误、是否改变既有行为。
6. **从真实场景抽象**：需求来自多个真实用户故事的共同点，不从单一个案机械地加功能。
7. **两步法顺序不可颠倒**：先以文字描述决策，再在文字定稿的基础上做原型；无界面产品（编译器、SDK、CLI 等）只做第一步。
8. **设计文档只读演化**：定稿即冻结，变更另写新版，保持旧判断可追溯。
9. **验证不了就标 TBD**：竞品结论、用户痛点、阈值数字，没有来源就标注待确认，不编造。
10. **AI 提效，人做取舍**：AI 可显著提升产出效率，但每个取舍由人决定、且可被否决；详实是为了让判断有依据，不是以篇幅替代判断。

## 先定场景

动手前宣布两项判定，用户可纠正：

- **有无界面**：有界面（App、Web、IDE 插件等）→ 文字稿与原型两步都要；无界面（编译器、SDK、CLI、协议等）→ 只做文字稿，原型 / Demo 字段免填。
- **规格粒度**：`MiniSpec`（小改动、决策点明显）用短模板讲清即可；`FullSpec`（影响持久、面广）需展开边界、备选方案与验收标准。不对小改动套完整模板，也不让大改动流于草率。

载体随协作场景：团队项目写入 Issue 并按标签流转（见「状态流转」）；个人项目可写入仓库 `docs/` 或 Issue，标签可裁，但「决策三要素、两步法、只读演化」不裁。

## 先写回理解

调研与动笔之前，先用几行字写回理解：

- 要解决什么问题、为谁做、成功长什么样；
- 把「用户明确说的」与「我的假设」分开列出，未定的标 TBD；
- 请用户纠正后再继续。

这一步对齐的是方向，不是措辞；理解在此刻被纠正的代价，远小于设计定稿后返工。

## 主流程

1. **行业与竞品调研**：调研该问题在行业中的通行做法、相关竞品及其取舍，梳理各方做法、优劣，以及可借鉴与应规避之处。结论须有据（链接或真实使用证据），不编造竞品能力。产出载体自定（协作文档、Wiki 皆可），组内有共识即可，不要求写入 Issue。
2. **讨论达成共识**：基于调研结果讨论，收敛出统一方向，形成初步设计。共识须在此阶段达成，避免后续各自为据。
3. **两步法细化**：
   - 第一步 文字描述：以纯决策表达写清解决什么问题、要什么、不要什么、边界何在，不涉及界面。
   - 第二步 原型：在文字定稿的基础上将交互与形态具象化。尚无基础代码时可用原型工具独立完成，本地跑通即可；仓库已有真实工程代码后，原型应建立在真实代码之上，以「只用于展示、不合并的 PR」承载，避免与线上逻辑脱节。原型图 / 链接直接附在文字稿之下，不单独为 UI 设计建 Issue。
4. **定稿为 Proposal**：整理为一份产品提案，写入 Issue（团队）或设计文档（个人）。逐行评审可借助不合并的草案 PR 进行，定稿后落回 Issue；此后只读，变更另写新版。

## Proposal 应包含的内容

| 字段 | 说明 |
| --- | --- |
| 动机 / 用户故事 | 哪些真实场景或痛点触发了它，共同需求一句话提炼 |
| 目标用户 | 为谁而做 |
| 现有做法及其不足 | 用户当前如何解决、尚存哪些冗余或手动负担；无则填「无」 |
| 本期范围与明确不做 | 做什么；明确列出本期不做的（非平凡提案必填） |
| 关键决策与依据 | 核心规则或方案；有哪几种做法、选择哪个、为什么（含竞品 / 替代方案） |
| 基本概念与信息结构 | 领域核心概念如何定义、信息 / 数据如何组织——作为架构设计的输入 |
| 原型 / Demo | 有界面的产品，附文字定稿后的原型；无界面产品免填 |
| 验收标准 | 何为达成——以具体例子表达、可独立验证、与实现技术无关 |

模板与两种粒度的写法见 `references/proposal-template.md`。

## 以例子定义行为

例子不是插图，是规范本身。每个关键行为给出：

- **现状**：现在怎么走、长什么样；
- **提议后的形态**：设计生效后的样子；
- **边界与非法情况**：哪些输入合法、哪些报错、冲突或省略时如何取舍。

交互行为可用 Given/When/Then 表达（Given 初始状态、When 角色操作、Then 可观察结果）。「现状 / 提议后 / 非法情况」三段式，比大段抽象描述更能让评审理解、让实现有据可依——这也是「详实具体」的落点。

## 状态流转

定稿前后以标签标记状态（标签体系与 Issue 治理沿用 `github-engineering-workflow`，此处不重复定义）：

- `proposal`：草案，设计进行中，可讨论、可修改。
- `Proposal-Accepted`：通过并进入开发；此后只读，变更另写新版。
- `Proposal-Denied`：方案不成立，记录理由后归档。被拒绝属正常结果，非失败。
- `Proposal-NoPlan`：方案成立但本期不做，记录后留待后续。

粒度以 `FullSpec` / `MiniSpec` 标签区分。真实样例（含通过与被拒）见 `references/process.md`。

## 与其他 skill 的分工

- 本 skill 负责开发前的产品设计决策：调研、取舍、两步法、Proposal 的内容质量。
- `github-engineering-workflow` 负责流程载体：Issue、标签、Milestone、PR 链路与个人/团队裁剪。
- `code-implementation` 负责 Proposal 被接受之后的实现；`code-review` 负责实现的审查。

## 红旗

| 想法 | 实际 |
| --- | --- |
| 「把功能点列全就是设计文档」 | 没有备选与取舍的功能清单不是产品设计；每个设计点补「几种做法、选了哪个、为什么」 |
| 「先画个原型看看，文字后面补」 | 顺序颠倒；原型必须建立在文字定稿之上，否则讨论的是界面而不是决策 |
| 「一份提案把相关需求都定了」 | 一次一个增量；相邻决策拆给后续 Proposal |
| 「小改动也套完整模板显得规范」 | 详略随影响面；MiniSpec 把字段讲清即可 |
| 「大改动先写两行，细节边做边定」 | FullSpec 必须展开边界、备选与验收，不接受草率 |
| 「竞品大概是这样，先写上」 | 没有来源的竞品结论标 TBD 或先去验证，不编 |
| 「需求变了，直接改原文档」 | 定稿只读；另写一份描述变化，保留旧判断可追溯 |
| 「方案被拒就是失败」 | 记录理由归档即正常结果；早拒掉错误方向正是产品设计的价值 |

## 验收清单

一份产品设计文档满足以下条件方为通过：

- [ ] 写回理解已经用户确认，假设与 TBD 显式标出。
- [ ] 设计方向经过行业与竞品调研，结论有据可循。
- [ ] 明确要什么、不要什么，本期边界清晰。
- [ ] 关键设计点具备备选方案与选择理由，而非功能罗列。
- [ ] 基本概念与信息结构清晰，可直接交付架构设计。
- [ ] 有界面的产品，文字定稿后具备对应原型。
- [ ] 行为以「现状 / 提议后 / 边界」例子定义，验收标准可据此验证。
- [ ] 状态与粒度标签齐全，可追溯。

## 输出要求

完成产品设计后简洁输出：① 场景判定（有无界面、MiniSpec/FullSpec）与依据；② 调研结论要点与来源；③ 关键取舍清单（每个设计点：备选、选择、理由）；④ 明确不做的范围；⑤ Proposal 落点（Issue 链接或文档路径）与状态标签；⑥ 未定的 TBD 与下一步最小动作。
