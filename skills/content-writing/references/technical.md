# 技术文章细则

把「怎么做 / 为什么 / 原理」讲清楚，并让读者能复现。价值来自准确与可复现，不来自文采。

## 结构骨架（按需裁剪章节，不必全用）

1. **钩子**：先给结论或痛点，让读者 30 秒内知道「是否该继续读」。
2. **背景与适用边界**：谁适合看、什么版本、什么前置条件、本文不解决什么。
3. **原理**：为什么这样设计；关键概念、机制或权衡。
4. **方案 / 实现**：从最小可用开始，逐步递进；每步能验证。
5. **验证与结果**：给出可观察的结果（输出、性能、截图、数据）。
6. **常见坑**：真实踩过的坑 + 根因 + 规避方式。
7. **总结与引用**：回扣主旨 + 官方文档 / 源码 / 论文链接。

## 代码与命令规范

- 代码必须真实可运行；贴进环境能复现结果。禁止「看起来对」的伪代码。
- 命令需在目标环境实际执行过；标注操作系统、shell、工具与版本号。
- 每个代码块前说明它要解决什么、运行前提与预期输出。
- 长代码只贴关键片段，完整工程给仓库链接或步骤，不整段倾倒。
- 涉及 API / 配置 / 依赖时，写明版本与兼容性；不确定就标注「未经验证」。

## 准确性与可复现

- 每个结论有来源（官方文档、源码、RFC、实验数据、一手调试记录）；引用标注版本与时间。
- 实验结果给出可复现条件（硬件 / 数据 / 参数 / 命令），并说明单次结果的局限。
- 明确区分「事实」「推断」「个人观点」，不用说法上的含糊掩盖不确定性。
- 写清**适用边界与不适用场景**：什么时候不该用这个方案、有什么代价。

## 语气与长度

- 专业但克制，重信息密度，不堆抽象概念；术语首次出现给一句解释或链接。
- 面向「目标读者的先验知识」写，不多解释人人皆知、也不少说明关键前提。
- 一章讲一件事；小标题可用「怎么做 + 为什么」的结构，让扫读也能得到要点。
