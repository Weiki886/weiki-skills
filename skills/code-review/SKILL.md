# 代码审查规范

审查的对象是**一段变更**，不是整个仓库。目标不是挑错，而是判断这段变更**合进主干后代码整体健康度是否确有改善**。

## 核心原则

1. 通过标准是「整体健康度确有改善」，不是「和我会写的一样」。完美的代码不存在，不因风格偏好阻塞变更。
2. 先钉住 diff 基线再开始；说不清「在审哪两个点之间的差异」就不要开审。
3. **双轴分离**：规范符合度与需求符合度分开审、分开报，不合并、不互相排名。一个轴通过不能掩盖另一个轴失败。

**第三个视角（可选）**：两轴之外，另用「过工程」视角扫一遍——不必要的复杂度、重复造轮子、过度抽象。需要时见 `references/overengineering.md`。
4. 每条意见必须带「严重度 + 位置 + 依据 + 下一步行动」。「可执行」指让作者明确知道下一步该做什么，不要求完整补丁；连下一步行动都给不出的意见不发。
5. 仓库既有约定优先于本 Skill 默认；与仓库文档冲突时以仓库为准并说明。
6. AI 生成代码需要**更严**的审查，不是更松——它自信且看起来合理，恰恰在错的时候也一样自信。
7. 机械验证优先交给工具，人不重复逐项手查；但 Reviewer 仍要检查工具配置是否正确、是否存在绕过或忽略标记（`// eslint-disable`、`# type: ignore`、`@ts-ignore`、`skip`），并负责工具判断不了的语义、设计与意图。
8. 无证据不得声称审查通过；不以「本地跑过」推断 CI、测试与部署已验证。

## 先定场景

动手前先判断，据此决定审查强度：

- **self（自审 / 个人项目）**：你自己是唯一负责人。必做双轴 + 正确性 + 安全；架构与性能按改动性质取舍；可跳过意见格式化、SLO、多 Reviewer。底线是「变更做对了需求、没引入明显漏洞、主干仍可用」。
- **peer（他人变更 / 团队协作）**：完整流程。双轴 + 五维度 + 严重度分级 + 书面意见 + 明确 verdict；安全敏感与关键路径追加领域 Reviewer。

缺省判定：变更将进入他人依赖的主干、公开产物或生产环境 → 按 peer；个人一次性项目自用 → 按 self。混合场景按风险上探、不向下放松。

## 第一步：识别目标并钉住基线

先确认「这段变更是什么」，再选对应的 diff 命令，不要所有场景都套三点 diff：

1. 定 review target：
   - PR / 分支（有 base 与 head）→ `git diff <base>...HEAD`（三点，相对 merge-base）
   - 已暂存改动（staged）→ `git diff --cached`
   - 未暂存改动（unstaged）→ `git diff`
   - 当前 HEAD 以来全部 tracked 工作区改动 → `git diff HEAD`
   - untracked 文件不进入普通 diff，用 `git status --short` 或 `git ls-files --others --exclude-standard` 补出，视需要一并审
2. PR / 分支场景确认固定点（commit SHA、`main`、tag、`HEAD~3`、merge-base 均可），用户没给就问，不要自己猜一个。
3. 分支场景取提交列表：`git log <base>..HEAD --oneline`。
4. 开审前先验证基线可解析且 diff 非空（或明确指出工作区无改动）。基线错了或 diff 为空要在这一步失败，不要带着错误范围往下审。
5. 评估语义体积：先排除生成文件、lockfile、机械 rename/reformat，再判断是否大到一次审不完；审不完就反馈「需要拆分」并给出拆分建议，不要假装审完。

## 第二步：定位两个来源

- **需求来源**（轴 B 依据），按序查找：用户显式提供的 spec → PR 正文 / 验收标准（Acceptance Criteria）→ PR / commit 关联的 Issue → 仓库内 `docs/`、`specs/`、ADR 中与分支名匹配的文档 → commit message 作为补充定位线索。都找不到就问用户；用户明确说没有，则轴 B 标注「无需求来源，已跳过」，不要凭空替作者构造需求。优先把需求收敛成 3–10 条验收标准，再做轴 B，降低「凭理解脑补需求」的概率。
- **规范来源**（轴 A 依据）：仓库的 `AGENTS.md`、`CONTRIBUTING*`、`CODING_STANDARDS*`、`.editorconfig`、lint / formatter 配置、既有代码的实际写法。仓库无约定时才落到本 Skill 的默认清单。

## 双轴审查

两轴依据不同、结论独立，**分别出结论**：

- **轴 A｜规范符合度**：这段代码符合本仓库的写法与质量基线吗？逐条引用被违反的规范（文件 + 规则原文）。仓库无明文约定时，用五个质量维度（见 `references/checklist.md`）与设计坏味道基线（见 `references/smells.md`）作为兜底，且必须标注为「判断题」而非硬违规。
- **轴 B｜需求符合度**：这段代码忠实实现了需求吗？只报三类：① 需求要求但缺失或只做了一半；② 需求没要求却做了（范围蔓延）；③ 看起来实现了但实现方式是错的。每条引用需求原文对应句。

支持并发子 agent 时，两轴各派一个独立子 agent，共享同一份冻结事实快照（相同 diff、commit list、仓库规范与需求来源），但互不读取对方的 findings，避免锚定偏差；主流程只做汇总，不重排、不跨轴改严重度。

## 严重度分级

每条意见必须标级，与 `github-engineering-workflow` 的 Review 约定一致：

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| `blocking` | 正确性错误、安全漏洞、需求未实现、破坏兼容或无法回滚 | 必须修复后才能合并 |
| `question` | 缺少信息就无法判断对错 | 作者回答后再定级，不得跳过 |
| `nit` | 命名、可读性、局部写法等改进建议 | 作者可自行决定，不阻塞 |
| `fyi` | 背景补充、后续改进方向、与本次变更无关的观察 | 不要求处理，建议转 Issue |

只有 `blocking` 能阻塞合并。把偏好写成 `blocking` 是滥用；把真实缺陷降级成 `nit` 是失职。

## 意见定位

定位以 `file:line` 优先；确实无法绑定到具体行时，允许降级为 `file/symbol`、`module` 或 `change-level / PR-level`。不要为了凑行号，把架构类或跨文件问题硬挂到不相关的一行上。

## 主流程

1. 定场景（self / peer），识别 target 并钉住基线，确认 diff 非空。
2. 定位需求来源与规范来源；缺需求来源就先问，别硬审。
3. 读懂变更意图：先看提交信息与需求，再看 diff；说不清「这段变更想干什么」就先问作者。
4. 风险扫描：读完 diff 先判断是否命中高风险面（认证/授权、密钥、SQL、文件上传、网络入口、支付、数据迁移、并发/竞态、反序列化、CI/CD、依赖变更）；命中才加载对应专项 checklist，普通 CRUD 不跑完整 OWASP。
5. 轴 A 与轴 B 分别审查（可并行子 agent，共享冻结事实快照）。
6. 跑可验证证据：测试、构建、lint、类型检查；记录实际命令与结果，不复述作者的说法。
7. 审测试质量：判断新增/修改的测试是否正确、有意义，代码坏掉时测试是否真的会失败；bug fix 在可行时验证回归测试在 base 上失败、在 HEAD 上通过。
8. 逐条整理意见：严重度 + 位置（`file:line` 优先）+ 依据 + 下一步行动。
9. 出 verdict：`Approve` / `Approve with nits` / `Request changes` / `Needs info`；给出理由。
10. `blocking` 全部关闭后增量复审：优先审本轮新增 delta，并回看被该 delta 影响的旧结论、调用点、测试与安全边界；不机械重审无关代码。

## 输出格式

```markdown
## 审查范围
基线 `<base>` → `HEAD`，共 N 个提交，M 个文件。需求来源：<Issue/spec 或「无」>

## 轴 A｜规范符合度
- `blocking` `src/a.ts:42` — 依据：<规范文件+规则 / 质量维度>。问题：<事实>。下一步：<下一步行动>。
- `nit` ...

## 轴 B｜需求符合度
- `blocking` — 需求原文：「<引用>」。现状：<缺失/多做/做错>。下一步：<下一步行动>。

## 验证证据
- 命令 → 结果（测试 / 构建 / lint / 类型）

## 结论
轴 A：<n 条，最严重 X>；轴 B：<n 条，最严重 Y>
Verdict：<Approve / Approve with nits / Request changes / Needs info>
```

两轴各自报「条数 + 本轴最严重问题」，不要跨轴评选一个「最大问题」——那正是双轴分离要避免的重排。

## 常见借口与现实

| 借口 | 现实 |
| --- | --- |
| 「能跑就行」 | 能跑但不可读、不安全、架构错的代码，债务会复利累积。 |
| 「我写的，我知道是对的」 | 作者对自己的假设是盲的。所有变更都值得第二双眼睛，包括你自己隔一天再看。 |
| 「测试过了就没问题」 | 测试是必要不充分条件，它不覆盖架构、安全与可读性。 |
| 「AI 写的应该没问题」 | AI 代码要更严的审查。它的自信与正确性无关。 |
| 「以后再重构」 | 以后不会来。审查就是那道闸门，在合并前要求修复，不是合并后。 |
| 「这个重构更干净了」 | 搬运复杂度不等于降低复杂度。读者要记住的概念数没减少，结构就没改善。 |
| 「只是加一个小分支」 | 小 diff 也会把文件推过健康体积、把逻辑挂到不相关流程上。判断结果结构，不是 diff 大小。 |
| 「只是升个版本号」 | 版本号变更是你没写的行为变更。读 changelog，SemVer 不保证不破坏。 |
| 「LGTM」 | 没有证据的 LGTM 等于没审。 |

## 红旗

- 未经任何审查直接合并；或只看 CI 是否绿就批准。
- 意见不标严重度，作者分不清哪些必须改。
- 安全敏感变更（认证、授权、支付、隐私、密钥、数据迁移、CI 配置）没有领域 Reviewer。
- 变更大到「没法好好审」却仍然批准。
- 修 bug 但不带回归测试。
- 重构只挪动代码，读者需要记住的概念数一点没少。
- 新增条件散落进不相关的代码路径（缺少抽象的信号）。
- 与既有 canonical 工具函数近似重复的自造实现；功能逻辑塞进共享模块。
- 锁文件被手改、未提交，或没看 diff 就合并。

## 接收审查意见

收到意见时不要表演式认同，也不要盲目照做。规则与话术见 `references/feedback.md`：先读完、复述、验证、评估，再实现或有理据地反驳。

## 输出要求

完成后简洁给出：① 审查范围与基线；② 轴 A / 轴 B 各自的意见清单与条数；③ 实际执行的验证命令与结果；④ verdict 与理由；⑤ 未能覆盖的部分与原因（如缺需求来源、无法运行测试、变更过大建议拆分）。不得把未验证的项目写成已验证。
