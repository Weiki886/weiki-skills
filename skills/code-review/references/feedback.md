# 审查意见的给出与接收

## 一、怎么写审查意见

### 意见四要素

缺任何一项都不要发出：

1. **严重度**：`blocking` / `question` / `nit` / `fyi`。
2. **位置**：以 `file:line` 优先；无法绑定具体行时降级为 `file/symbol`、`module` 或 `change-level / PR-level`，不要为凑行号硬挂到无关行。
3. **依据**：引用的规范条文、需求原文、或质量维度名称。不写「我觉得」。
4. **下一步行动**：让作者明确知道下一步该做什么，例如「为这个分支补一个并发回归测试」，不要求完整补丁。连下一步行动都给不出，先降级为 `question` 提问。

### 话术

- 说代码，不说人：写「这个函数在输入为空时会抛异常」，不写「你没考虑空输入」。
- 提问代替断言：不确定时写「这里为什么用 X 而不是 Y？」，而不是「这里应该用 Y」。
- 给出理由：「建议改成 X，因为 Y 在并发下会重复写入」比「改成 X」有用得多。
- 承认不确定：「我不熟悉这块，可能想错了——」这句话不会削弱意见，反而会让作者更愿意解释。
- 明确非阻塞：`nit` 和 `fyi` 要写清「不阻塞合并，你可以自行决定」。

### 反模式

- 无证据的 `LGTM`。
- 把个人风格偏好写成 `blocking`。
- 把真实缺陷降级成 `nit` 以免得罪人。
- 在审查里顺手重新设计整个模块（该转 Issue）。
- 一次抛出 30 条 nit 却漏了正确性问题。
- 只指出问题不给方向，让作者反复猜。

### 分歧处理

1. 先确认双方对事实的理解一致（是不是在说同一段代码、同一个场景）。
2. 分清是「事实分歧」还是「取舍分歧」：事实分歧靠证据（跑一遍、查文档）；取舍分歧靠约定。
3. 取舍分歧且双方都有道理时，作者的选择优先——除非它破坏了仓库明文规范。
4. 僵持不下时上升到第三人或维护者，不要在评论里反复拉锯。
5. 达成的结论写进仓库规范，避免下次重演同一场争论。

## 二、怎么接收审查意见

**审查需要的是技术评估，不是情绪表演。** 核心原则：先验证再实现，先问再假设，技术正确优先于社交舒适。

### 响应流程

```
收到审查意见时：

1. 读完   — 读完全部意见再做任何反应
2. 复述   — 用自己的话说清这条意见要求什么（说不清就问）
3. 验证   — 拿代码库的实际情况核对这条意见是否成立
4. 评估   — 对这个代码库来说，这个改法技术上确实更好吗
5. 回应   — 技术性确认，或有理据地反驳
6. 实现   — 一条一条改，每条改完各自验证
```

### 禁止的回应

**永远不要**：

- 「你说得完全对！」——谄媚式认同，且往往在还没验证时就说出口。
- 「这个点太好了！」「非常感谢您的宝贵意见！」——表演，零信息量。
- 「我马上改」——在验证之前就承诺，等于放弃技术判断。

**改成**：

- 复述这条意见的技术要求，确认理解一致。
- 不清楚就提问。
- 认为意见有误就带技术理由反驳。
- 想清楚了就直接动手——行动比表态有用。

### 意见不清楚时

```
如果任何一条意见不清楚：
  停下 — 先不要开始改任何东西
  问清那几条不清楚的意见
  等回答，再一起规划改动顺序
```

不要「先改懂的那几条，不懂的等等再说」——半懂状态下的改动通常要重做。

### 反驳的正确姿势

反驳不是不礼貌，盲从才是不负责。带上这三样：

1. **事实**：代码库里的实际情况（贴出相关代码、配置或测试）。
2. **后果**：按意见改会导致什么具体问题。
3. **替代**：如果对方指出的问题真实存在，你提议怎么解。

例：「这个位置加缓存会让 `X` 的失效逻辑和 `Y` 冲突（`cache.ts:88` 已经在这里失效一次）。如果目的是降延迟，改成在 `Y` 那层缓存可以避免双写——要不要我先测一版？」

### 实现意见时

- 一条一条改，每条改完单独验证，不要一把梭。
- 每条意见明确回应状态：已改（附 commit）/ 已延后（附理由与 Issue）/ 不改（附技术理由）。
- 改动过程中发现意见本身有问题，回到反驳流程，不要闷头改成半对半错。
- 所有 `blocking` 关闭后主动请复查，并说明这次改了哪些、怎么验证的。
