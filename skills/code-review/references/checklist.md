# 质量维度与检查清单

仓库有明文规范时以仓库为准；本文件是仓库无约定时的兜底基线。所有条目都是**判断题**，不是硬性违规——发现时标为待确认，由变更的实际上下文决定是否成立。

## 五个质量维度

### 1. 正确性

代码是否真的做了它声称的事？

- 是否匹配需求与验收标准？
- 边界条件是否处理：null、空集合、0、负数、超长输入、并发首次/末次。
- 错误路径是否处理，而不是只写了 happy path？异常被捕获后是被处理还是被吞掉？
- 是否存在 off-by-one、竞态、状态不一致、时区/编码假设？
- 测试是否真的在测该测的东西？断言是否可能永真？
- 幂等性与重试：这段逻辑被重复执行两次结果是否一致？

### 2. 可读性与简洁

另一个工程师（或 agent）不看作者解释能不能读懂？

- 命名是否表意，且与仓库既有命名一致？`temp`、`data`、`result`、`handle` 这类无上下文名字要追问。
- 控制流是否直白？嵌套三元、深层回调、超长函数要指出。
- **同样的事能不能用更少的代码做完**？1000 行做 100 行的事本身就是问题。
- **抽象是否配得上它带来的复杂度**？第三次出现同一需求前不要提前泛化。
- 是否残留死代码：未使用变量、`// 已废弃` 注释、为兼容而留的空壳。
- 注释是否解释了「为什么」而不是复述「做了什么」？
- **新条件是否被硬挂到不相关的流程上**？这是设计问题不是 nit，应当抽成独立的辅助函数、状态或策略。

### 3. 架构

变更是否契合系统既有设计？

- 沿用既有模式还是引入新模式？引入新模式是否有说明？
- 模块边界是否清晰？依赖方向是否正确、有无环依赖？
- 是否有该共享却重复的实现？
- **这次重构是降低了复杂度还是只搬运了复杂度**？数一下读者要同时记住的概念数：如果「更干净」的版本概念数没变，它就没更干净。优先选让整条分支/模式/层次消失的改法，而不是把同样的逻辑重新集中一处。
- **功能专属逻辑是否泄漏进共享模块或通用工具**？逻辑应留在其归属层，复用既有 canonical 实现而不是造近似重复品。
- **类型边界是否明确**？可疑的 `any` / `unknown` / 随手可选 / 强制转换 / 静默兜底，往往在掩盖一个说不清的不变量；把边界写明确通常反而让控制流变简单。

### 4. 安全

- 用户输入是否在边界处校验与净化？
- 密钥、凭据、token 是否进了代码、日志、错误信息或版本库？
- 认证与授权检查是否到位？是否存在越权读写（IDOR）？
- SQL 是否参数化，没有字符串拼接？命令执行是否有注入面？
- 输出是否做了编码以防 XSS？
- 外部来源数据（API 响应、日志、用户内容、配置文件）是否被当作不可信处理？
- 依赖是否可信、无已知漏洞？锁文件是否随之更新？
- 报错信息是否泄漏了内部结构、路径或堆栈？

### 5. 性能

- 是否引入 N+1 查询？
- 是否有无界循环、无限制的数据拉取、缺失分页的列表接口？
- 该异步的操作是否写成了同步阻塞？
- 是否有不必要的重复渲染或重复计算？
- 是否在热路径上创建大对象、做重复序列化？
- 索引是否配套？新查询条件是否命中索引？

性能问题只在「有实际影响」时才提；没有度量就说「这里慢」属于猜测，标 `question` 而不是 `blocking`。

## 按变更类型的专项检查

| 变更类型 | 额外必查 |
| --- | --- |
| 修 bug | 是否带回归测试？测试在修复前是否会失败？根因是否修掉而不是掩盖症状？ |
| 新功能 | 是否有开关/灰度？失败时的降级行为是什么？是否影响既有行为？ |
| 重构 | 行为是否严格不变？是否有测试保护？概念数是否真的减少？ |
| 数据库迁移 | 能否回滚？大表操作是否会锁？是否兼容新旧两版代码同时运行？ |
| 依赖升级 | 是否读了 changelog？是否一次只升一个包？锁文件 diff 是否看过？ |
| API 变更 | 是否破坏兼容？是否有版本策略与废弃期？文档是否同步？ |
| 配置 / CI | 是否可能泄漏凭据？失败时是否会静默通过？权限是否最小化？ |
| 删除代码 | 是否确认无调用方？是否有外部依赖此行为？ |

## 审查测试质量

测试本身是审查对象，不是背景绿光。对 AI 生成代码尤其重要——它很容易同时产出「错误实现 + 与错误实现一致的测试」，最后全绿。

- 新增/修改的测试是否正确？断言的是**被测行为**，而不是实现细节或永真条件（`expect(x).toBeDefined()`）。
- 「把实现改错，测试还会绿吗？」——用这个检验测试是否真的能失败。
- 覆盖了边界与错误路径，而不只是 happy path？
- mock 是否把被测逻辑本身也 mock 掉了（测了个寂寞）？
- bug fix：可行时把修复撤掉（或在 base 上）跑一次，回归测试应**失败**；在 HEAD 上应**通过**。
- 覆盖率上升 ≠ 质量：量化交给工具，语义交给 Reviewer。

## 风险触发的安全专项

读完 diff 先做轻量风险扫描；只有命中才加载本专项，普通 CRUD 不跑完整 OWASP。

命中即加载的高风险面：

- 认证 / 授权 / 会话（越权、IDOR、权限绕过）
- 密钥、凭据、token 的存储与传输
- SQL / 命令 / 模板 / 反序列化注入面
- 文件上传、网络入口、外部数据流
- 支付、资金、数据迁移（含回滚与新旧版本兼容）
- 并发 / 竞态 / 事务完整性
- CI/CD 配置、依赖变更、供应链

对应逐条检查（命中才查）：

- [ ] 认证授权：默认拒绝而非默认放行；越权路径已测
- [ ] 密钥：不落代码/日志/提交；传输加密；权限最小化
- [ ] 注入：SQL 参数化、命令不拼接、模板转义、反序列化白名单
- [ ] 上传：类型/大小/内容校验，存到非执行路径
- [ ] 迁移：可回滚、大表不锁、新旧两版代码共存
- [ ] 并发：幂等与重试、race condition、事务边界
- [ ] 依赖：逐包审查 changelog、一次只升一个、看 lockfile diff、查已知漏洞与许可证

## 完整勾选清单


peer 场景建议逐项确认；self 场景至少覆盖「正确性 + 安全 + 需求符合度」。

```markdown
## 审查：<变更标题>

### 上下文
- [ ] 我说得清这次变更做了什么、为什么做
- [ ] 基线已钉住，diff 范围确认无误
- [ ] 需求来源已定位（或已确认不存在）

### 正确性
- [ ] 匹配需求与验收标准
- [ ] 边界条件已处理
- [ ] 错误路径已处理，异常没被吞掉
- [ ] 测试确实覆盖了本次变更

### 可读性
- [ ] 命名表意且与仓库一致
- [ ] 控制流直白，无多余复杂度
- [ ] 无死代码残留

### 架构
- [ ] 沿用既有模式，或新模式有说明
- [ ] 依赖方向正确，无环依赖
- [ ] 抽象层级恰当，未提前泛化
- [ ] 重构确实降低了概念数，而非搬运复杂度
- [ ] 功能逻辑未泄漏进共享模块，文件体积仍健康

### 安全
- [ ] 无密钥、凭据入库或入日志
- [ ] 输入在边界处校验
- [ ] 无注入面（SQL / 命令 / 模板）
- [ ] 认证授权检查到位
- [ ] 外部数据按不可信处理

### 性能
- [ ] 无 N+1
- [ ] 无无界操作，列表接口有分页

### 验证
- [ ] 测试通过（记录命令与结果）
- [ ] 构建成功
- [ ] lint / 类型检查通过
- [ ] 必要的人工验证已完成

### 结论
- [ ] Approve — 可以合并
- [ ] Approve with nits — 可合并，附非阻塞建议
- [ ] Request changes — 存在 blocking 问题
- [ ] Needs info — 信息不足，无法判断
```

## 复查

`blocking` 全部处理后：

- [ ] 所有 `blocking` 已解决，或已明确记录延后理由与责任人
- [ ] 测试、构建、lint 重新通过
- [ ] 优先审本轮新增 delta，并回看受该 delta 影响的旧结论、调用点、测试与安全边界，未机械重审无关代码
- [ ] 验证过程已记录（改了什么、怎么验证的）
