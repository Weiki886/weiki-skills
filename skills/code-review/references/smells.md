# 设计坏味道基线

两条约束先立在这里：

- **仓库优先**：仓库明文规范总是胜过本基线。仓库明确认可某种写法时，抑制对应坏味道，不要拿本文件去推翻仓库约定。
- **永远是判断题**：每条都写成「疑似 X」而非「违反 X」。工具已经强制的（格式、lint、类型）不在此列，不要重复报。

每条读法：**它是什么 → 怎么改**。逐条对着 diff 匹配，不匹配就跳过。

## 经典坏味道（Fowler《重构》第 3 章）

| 坏味道 | 它是什么 | 怎么改 |
| --- | --- | --- |
| 神秘命名 | 函数、变量或类型的名字没有透露它做什么、装什么 | 改名；如果起不出一个诚实的名字，说明设计本身没想清 |
| 重复代码 | 同一段逻辑形状出现在多个 hunk 或文件里 | 抽出共享形状，两处都调用它 |
| 依恋情结 | 一个方法访问别的对象的数据比访问自己的还多 | 把方法搬到它依恋的数据那边去 |
| 数据泥团 | 同样几个字段/参数总是一起出现（一个想要诞生的类型） | 打包成一个类型，传这个类型 |
| 基本类型偏执 | 用原始类型或字符串充当本该有自己类型的领域概念 | 给这个概念一个小类型 |
| 重复的 switch | 对同一类型的 `switch` / `if` 级联在变更中反复出现 | 换成多态，或让两处共享同一张映射表 |
| 霰弹式修改 | 一个逻辑改动被迫在 diff 里散着改很多文件 | 把一起变的东西收进同一个模块 |
| 发散式变化 | 同一个文件或模块因为多个互不相关的原因被修改 | 拆开，让每个模块只因一个原因改变 |
| 夸夸其谈通用性 | 为需求里根本没有的场景加抽象、参数或钩子 | 删掉；先内联回去，等真实需求出现再说 |
| 过长的消息链 | 调用方依赖 `a.b().c().d()` 这样的长导航 | 把这次遍历隐藏到第一个对象的一个方法后面 |
| 中间人 | 一个类或函数大部分工作只是把调用转发出去 | 去掉它，直接调真正的目标 |
| 被拒绝的遗赠 | 子类或实现者忽略/覆盖了它继承来的大部分东西 | 放弃继承，改用组合 |

## AI 生成代码特有的坏味道

AI 写的代码需要更严的审查。以下模式在 AI 产出中出现频率显著更高：

| 坏味道 | 表现 | 怎么改 |
| --- | --- | --- |
| 幻觉 API | 调用了看起来很合理但实际不存在的方法、参数或配置项 | 逐个核对官方文档与实际类型定义，不要相信「看起来对」 |
| 防御性过头 | 到处加 try/catch、可选链、默认值，把该暴露的错误全兜住 | 只在真正的边界处兜；内部不变量该崩就崩，静默兜底会掩盖 bug |
| 注释复述代码 | `// 遍历用户列表` 紧跟着一个 for 循环 | 删掉复述型注释，只保留解释「为什么」的 |
| 教科书式抽象 | 为一个只有一处调用的功能造出接口 + 工厂 + 策略三件套 | 内联回去，等第三次出现再抽 |
| 与仓库风格断裂 | 命名、错误处理、日志、目录组织跟仓库既有写法不一致 | 对齐仓库既有写法，不要引入第二套风格 |
| 编造的测试 | 断言可能永真（`expect(result).toBeDefined()`）、mock 掉了被测逻辑本身 | 要求测试在功能被破坏时会失败，否则等于没测 |
| 看似完整的实现 | 主流程写得很漂亮，但边界、错误、并发路径是空的或 TODO | 按正确性维度逐条追问边界与错误路径 |
| 数字与事实杜撰 | 注释或文档里写出没有来源的性能数字、版本号、限制值 | 要求来源；给不出就删 |

## 推定阻塞项

以下情况先按「提出问题 + 给出更简方案」处理，标 `question`；只有当变更确实让结构更糟时才升级为 `blocking`：

- 重构搬运了复杂度而没有降低它。
- 变更把文件推过健康体积却没有做拆分。
- 功能逻辑被加进共享模块。
- 造了一个与既有 canonical 实现近似重复的东西。
- 静默兜底掩盖了一个说不清的不变量。
