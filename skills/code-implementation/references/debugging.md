# 系统化调试

铁律：

```
没有根因调查，就没有修复。改症状 = 失败。
```

## 何时用

任何技术问题：测试失败、生产 bug、意外行为、性能问题、构建失败、集成问题。**尤其**在赶时间、「一眼就看出修法」、已经试过多次、上一次修没生效、或你没完全理解问题时——这些恰恰是最容易被「猜一修»带偏的时刻。

不要因为「问题看起来简单」或「在赶进度」就跳过。系统化比反复乱试更快。

## 四阶段：逐阶段完成才能进下一个

### Phase 1｜根因调查（动手修之前）

先侦查，后行动：在动手改任何代码之前，先用实际运行中的证据来回答「问题到底在哪」。截屏、抓日志、读控制台输出、看 DOM 状态——先让证据说话，再形成假设，不要凭直觉直奔「修法」。

1. **把报错读完整**：错误、警告、完整栈、行号、文件、错误码，往往就写着答案。
2. **稳定复现**：触发步骤是什么？每次必现吗？复现不了就先补数据，别猜。
3. **查最近改动**：`git diff`、近期 commit、新依赖、配置变化、环境差异。
4. **多组件系统加证据**：在每层边界打点，看数据进 / 出各层的样子，先定位「坏在哪一层」，再深入那一层。
5. **沿数据流回溯**：坏值从哪来？谁用坏值调用它？一直向上追到源头；在源头修，不在症状处修。

### Phase 2｜模式分析（找到规律再修）

1. **找能跑通的对照**：代码库里有没有类似但能正常工作的实现？
2. **读参考实现到完整**：是别人写好的模式就逐行读完，别扫一眼。
3. **逐条列差异**：能跑的与不能跑的到底差在哪，一条别漏，别「觉得这不重要」。
4. **理清依赖**：这段还依赖什么组件、配置、环境、假设。

### Phase 3｜假设与验证（科学方法）

1. **一次只立一个假设**，写成「我认为 X 是根因，因为 Y」。
2. **做最小改动**验证它：一次只动一个变量。
3. **验证再继续**：成了 → Phase 4；没成 → 立新假设，不要在旧假设上再叠补丁。

### Phase 4｜修复并回归

1. 修在根因处：先 `grep` 该函数 / 模块的所有调用方，确认「所有路径」都经过修复点；在共享层修一次，而不是只修出问题的那条路径——否则每个兄弟调用方还是坏的。
2. 加 / 改测试固化，走一遍红绿（见 `tdd.md`）。
3. 全量跑测试与相关验证，确认没引入回归。

## 常见反例

| 行为 | 为什么错 |
| --- | --- |
| 报错没读完就上手改 | 答案常在报错信息里 |
| 不复现就修 | 修的可能根本不是这个 bug |
| 一次试三个修法 | 不知道是哪个起效，等于没学会 |
| 在症状处打补丁 | 根因还在，换条路径照样炸 |
| 「先改一下看看效果」 | 这不是调试，是碰运气 |
| 修完不回归 | 老 bug 换张脸回来 |

## 卡住时的唯一解

停止加补丁。回到 Phase 1 重新收集证据，或带着「已排除的假设 + 当前证据」回到需求方 / 同伴求助；不要靠猜硬扛。
