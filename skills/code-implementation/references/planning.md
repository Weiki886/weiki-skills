# 写实现计划

把澄清后的需求，拆成能**独立验证、独立提交**的小任务。计划要写给「对仓库零上下文、品味存疑」的执行者看——包括未来的自己。

## 计划结构

```markdown
# [特性名] 实现计划

**目标**：<一句话说清构建什么>

**架构**：<2–3 句说明思路>

**技术栈**：<关键技术与库>

**需求依据**：<指向澄清后的需求块 / 设计文档 / issue，执行时两者都要读>

## 全局约束

<需求里贯穿全项目的硬约束——版本下限、依赖限制、命名与文案规则、平台要求，
每条一行，原文照抄。下面的每个任务都隐式继承它。>

---

### Task N: [组件名]

**文件**
- 新增：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

**接口**
- 消费：<引用前序任务产出的类型 / 函数签名>
- 产出：<后续任务依赖的名字与签名，精确到参数与返回类型>

- [ ] **步骤 1：写失败测试**（贴真实测试代码）
- [ ] **步骤 2：运行并确认失败**（命令 + 预期失败原因）
- [ ] **步骤 3：写最小实现**（贴真实实现代码）
- [ ] **步骤 4：运行并确认通过**（命令 + 预期 PASS）
- [ ] **步骤 5：提交**（`git add` + Conventional Commits 信息）
```

## 任务切分

- 一个任务是最小的「自带一次测试循环、值得被 Reviewer 单独放行」的单元。
- 把配置、脚手架、文档等杂活，折叠进「需要它的那个交付物」所对应的任务里，不单独立项。
- 只在「Reviewer 可能拒绝 A 却放行 B」处切开任务边界。
- 每个步骤是一个动作（2–5 分钟量级）：写失败测试、跑失败、写实现、跑通过、提交——五步正好。

## 文件分组

- 一个文件一个清晰职责；小而专注的文件比大而全的更好改、更好审。
- 一起变的东西放一起；按职责切分，不按「技术层」切。
- 沿用仓库既有结构；不要为「显得更干净」强行重排。只有当你正改的文件确实臃肿时，才在计划里顺手做一次拆分。

## 无占位符

计划里每个步骤都要有执行者真正需要的内容。以下都是「计划失败」，禁止出现：

| 占位符写法 | 为什么不行 |
| --- | --- |
| TODO / TBD /「稍后实现 / 填细节」 | 执行者不知道下一步 |
| 「适当处理异常 / 加校验 / 处理边界」 | 没给具体规则 |
| 「给上面的写测试」却不带测试代码 | 等于没写 |
| 「类似 Task N」 | 执行者可能乱序读任务，必须重复真实代码 |
| 只描述「做什么」不展示「怎么做」 | 代码步骤必须有代码块 |

引用任何类型 / 函数 / 方法，都必须在本计划的某个任务里被定义过；不能引用「计划里不存在」的符号。

## 写完自检

计划写完后，用新眼光对照需求过一遍（自己跑，不派子代理）：

1. **spec 覆盖**：逐条扫需求 / 验收标准，能否指出某个任务实现了它；列缺口、补任务。
2. **占位符扫描**：搜 TODO、「适当」「类似 Task N」等红线词，逐个消除。
3. **类型对齐**：后面任务用的签名、字段名，是否与前面任务定义的一致；`clearLayers()` 前脚叫 `clearFullLayers()` 后脚换了名就是 bug。
4. **接口连续**：每个任务「消费」的，确实由前序任务「产出」；没有悬空依赖。

发现问题就地修，不必二次评审——修完继续，直到四关都过。

## 执行交接

计划落盘后，给执行两条路二选一，不要自己闷头开跑：

1. **子代理逐任务执行**：每任务派一个干净子代理 + 任务间复核，适合较大实现。
2. **本会话顺序执行**：按清单逐任务跑，每任务有检查点。

两种情况都遵守 `references/tdd.md` 的红绿门。

## 执行纪律

### 台账（ledger）

记忆会丢、上下文会被压缩，台账不会。执行时维护一份进度台账（仓库内 gitignore 的临时文件即可）：

```text
# 执行台账 — 计划：<计划名>

- Task 1: complete — `pytest tests/x.py` 12 passed
- Task 2: in progress
- Task 2: Ruling: 计划签名是 clearLayers()，既有代码叫 clearFullLayers() —— 沿用既有名字 —— 错了的代价：Task 4 消费方要同步改名
```

- 每个任务完成记一行：命令 + 真实结果；中断或上下文压缩后，凭台账和 `git log` 恢复，不凭记忆重做。
- 记账随工作顺手做（和提交同一步），不单独来回翻账。

### 计划错还是代码错

每步的实际输出与计划预期不符时，先分流：

- **代码错**：走 `debugging.md`，找根因，不许改症状凑出预期输出。
- **计划错**（计划自相矛盾、与需求 / 既有接口冲突、命令本身跑不通）：按「满足需求的最小改动」当场裁决，并记一条
  `Ruling: <发现> — <决定与理由> — <错了的代价>`，然后继续。后续任务碰到同一接口时先读这条裁决。

没有 Ruling 的偏离 = 偷偷做的决定，等同于无记录返工。

### 连续执行与停止条件

选定顺序执行后，在用户授权范围内连续跑完计划，不在每个任务后停下来问「要继续吗」。遇到以下情况且缺少授权或必要信息时暂停：

1. 不可逆或破坏性操作；
2. 安全敏感动作（凭据、权限、对外暴露）；
3. 工作区之外的副作用（合并、推共享分支、发布）；
4. 计划烂到每条路都只能靠猜——带上「已排除的假设 + 当前证据」回来问。

已有明确授权且目标清晰的操作不重复请示；计划和 Ruling 都不能替代用户授权。其他无法安全推进的阻塞也应如实报告，不强行套进上述四类。歧义若能依据需求或计划裁决，按 Ruling 处理后继续，不属于停止条件。
