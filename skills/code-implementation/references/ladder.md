# 爬梯子：写代码前先问七层

写任何代码之前，先理解问题，再爬梯子。停在第一层能站稳的 rung——不是停在「第一层看起来能行」，而是停在「第一层真实覆盖需求」。

## 七层梯子

| 层 | 问题 | 怎么做 |
| --- | --- | --- |
| 1 | **这真的需要存在吗？** | 拍脑袋的需求 → 不写，一句话说清为什么不需要。 |
| 2 | **仓库里已经有了？** | 先搜再写：helper、util、type、既有模式，几行外可能就躺着。 |
| 3 | **标准库有吗？** | `pathlib > os.path`，`datetime > 手写时间解析`。 |
| 4 | **平台原生能力？** | `<input type="date">` 而非日期选择库，CSS 而非 JS 动画，DB 约束而非应用层校验。 |
| 5 | **已装依赖能解？** | 翻 `package.json` / `requirements.txt`，别为一个函数加新依赖。 |
| 6 | **一行能搞定？** | 一行代码，不写一个文件。 |
| 7 | **都不是，才写** | 最少的、能工作的代码，没被要求的一律不写。 |

两层同时成立 → 取高的一层。找到就停，不继续往下爬。

## 梯子怎么用

- 梯子是**肌肉记忆**，不是研究项目——先读懂问题、读完受影响的代码、跑通实际流程，再爬。
- 对**懒在解法上，不懒在理解上**：跳过理解去追求小 diff，是危险的那种懒。
- 两个 rung 都能用 → 取高的那个，立刻用，不纠结。

## 不砍的东西

以下永远不在梯子上：

- 信任边界的输入验证
- 防止数据丢失的错误处理
- 安全措施（认证、授权、加密）
- 无障碍基础
- 用户明确要求的东西

梯子砍的是「不必要的复杂度」，不是「必要的安全」。

## 故意简化

当某个简化确实牺牲了通用性 / 性能，但当前够用，用注释标记天花板和升级路径：

```
# ponytail: 全局锁，如果吞吐量成瓶颈改为按账户粒度锁
```

不写注释的故意简化 = 埋雷。

## 输出

写完代码后，最多三行说清：跳过了什么、什么时候该加回来。解释比代码长 → 删解释，用长篇大论为简化辩护 = 把复杂度走私回来说明文里。

## 反例

| 行为 | 梯子哪层没爬 |
| --- | --- |
| 用户要个日期选择器，装 flatpickr 写组件 | 第 4 层：`<input type="date">` |
| 自己写了个 `leftPad` 函数 | 第 3 层：`String.prototype.padStart` |
| 加了个 `lodash` 只为用 `_.cloneDeep` | 第 5 层：`structuredClone` 已在标准库 |
| 写了个接口和一个实现，以后会有第二个 | 第 1 层：以后不会来 |
