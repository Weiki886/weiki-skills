# 交付前验证

铁律：

```
没有新鲜验证证据，就没有「完成 / 通过 / 修好了」这类结论。
```

如果你这一节没实际跑过那条命令，就不许声称它通过。

## 验证门（五步）

声称任何状态之前：

1. **认清**：哪条命令能证明这个结论？
2. **跑全**：完整、新鲜地执行整条命令。
3. **读全**：看完整输出、退出码、失败数。
4. **核实**：输出是否真的支持这个结论？不支持 → 如实报「当前状态 + 证据」；支持 → 报「结论 + 证据」。
5. **才下结论**：跳过任何一步 = 没验证，等于撒谎。

## 常见伪证据

| 结论 | 需要 | 不够 |
| --- | --- | --- |
| 测试通过 | 测试命令输出 0 失败 | 上次跑过、「应该能过」 |
| lint 干净 | lint 输出 0 错误 | 只查了一部分、推算 |
| 格式化完成 | formatter 输出 0 改动 | 记得跑过、看起来对齐 |
| 构建成功 | 构建命令退出码 0 | lint 过了、日志看着还行 |
| bug 已修 | 复现该症状的测试通过 | 改了代码、以为修了 |
| 回归测试有效 | 上测试跑通、去掉修复后必失败、装回修复再跑通 | 只跑通过一次 |
| 验收达成 | 逐条对验收标准打勾 | 测试全绿 |
| 子代理干完了 | 看 VCS diff 确认真改了 | 子代理自称成功 |

## 红线（立刻停）

- 「应该 / 可能 / 看起来 / 似乎」这类措辞。
- 没跑验证就说「搞定 / 完成了 / 完美」。
- 准备 commit / push / 开 PR 前还没验证。
- 信任子代理或 AI 的「成功」自述。
- 只做了部分验证（lint 过了不等于能编译）。
- 心想「就这一次不跑了」。

## 常用证据样板

- ✅ `pytest` → `34 passed` → 「34/34 通过」
- ✅ `npm run build` → `exit 0` → 「构建通过」
- ✅ 回归测试：写 → 跑（通过）→ 还原修复 → 跑（必失败）→ 装回 → 跑（通过）
- ✅ 验收：重读需求 → 建勾选清单 → 逐条核对 → 报缺口或完成

## 交付清单

逐条勾完才允许声称「完成」：

- [ ] 全量测试通过，输出干净（0 失败、0 错误）
- [ ] formatter 已跑，无未提交的格式改动
- [ ] linter 已跑，0 错误
- [ ] 构建成功（exit 0）
- [ ] 验收标准逐条核对通过
- [ ] 文档同步：代码变更涉及的 README / API doc / changelog 已更新；代码与文档不同步视为交付未完成

## 适用时机

以下情形**之前**必须先验证：

- 任何「完成 / 通过 / 修好」的表述，包括同义换说法。
- 提交、开 PR、标记任务完成、进入下一任务、把活交给子代理。

规则覆盖所有「暗示成功」的口径，不只盯字面措辞。
