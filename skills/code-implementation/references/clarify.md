# 澄清需求

模糊需求是返工的头号来源。写码前先把需求收敛成**可验收**的清单；收敛不了就继续问。

## 实现前 7 问

1. **要解决什么问题**：用户 / 业务侧的原始诉求是什么？这不是「要哪个页面的按钮」，而是背后的目标。
2. **验收标准**：怎么证明「做完了」？最好 3–10 条、可逐条勾选，而不是「能用」。
3. **边界**：明确不做哪些；「顺带做」的东西要排除在本次范围外。
4. **输入与输出**：数据从哪来、长什么样、出去给谁；异常输入怎么处理。
5. **约束**：技术栈、版本下限、性能 / 兼容 / 规范要求，逐条写清并保留原文数值。
6. **失败模式**：这条逻辑失败时会发生什么，可接受吗。
7. **可验证性**：我怎么在本地跑出「对或不对」的证据。

## design tree 拷问

需求跨多个决策时，别一次性抛一堆问题。把决策画成一棵树：每个决策下面挂着依赖它的子决策。

- **frontier（前沿）** = 所有「前置已定、现在就能问」的决策集合。
- 每轮只问整个 frontier；每个问题给编号 + 你的推荐答案，等用户答完再推进下一轮。
- 依赖尚未定决策的问题，归到更后面的轮次，不提前问。

分工原则：

| 类型 | 谁来做 |
| --- | --- |
| 查事实（仓库现状、工具行为、环境） | 你的活，别拿去问用户；查不清才把缺口报出来 |
| 做决策（方向、取舍、优先级） | 用户 / 需求方的活，逐条摆给他选 |

frontier 空了 = 每根分支都走到、没有「默默默认」的假设，此时才进入写计划。

## 常见模糊需求的红旗

- 「优化一下」「做得更好用」这类只有形容词、没有可观测指标。
- 「参考 XX 做一个」但既没给 XX 也没给差异点。
- 验收标准不再能客观判断对错。
- 范围随风涨：聊着聊着不断加入新功能。

## 产出

一段「确认过」的需求块，至少含：目标一句话、验收标准若干条、明确的非目标、关键约束。这段文字会作为写计划与最终验收的共同依据。
