# TDD 红绿重构

maintained 场景的铁律：

```
没有先失败过的测试，就没有生产代码。
```

先写生产代码再补测试？删掉，从测试重来。不「留作参考」、不「边写测试边改实现」——从测试开始重新实现。

## 何时用

**始终**：新功能、bug 修复、重构、行为变更。

**例外（先问用户）**：一次性原型、生成代码、纯配置文件。想「就这次跳过」？停下——那就是合理化借口。

## 红绿重构循环

### 1. RED｜写失败测试

写一个最小测试，说清「该发生什么」。要求：

- 一次只测一个行为；测试名里出现「and」往往该拆。
- 名字说清行为，不叫 `test1`。
- 用真实代码，能用就不要 mock；mock 只测 mock，不测实现。

```python
# 好：名字清楚、测真实行为、只测一件事
def test_retry_succeeds_after_third_attempt():
    attempts = 0
    def operation():
        nonlocal attempts
        attempts += 1
        if attempts < 3:
            raise RuntimeError("fail")
        return "success"

    assert retry_operation(operation) == "success"
    assert attempts == 3

# 坏：名字含糊、只测了 mock 被调用次数
def test_retry_works():
    fn = mock.Mock(side_effect=[RuntimeError, RuntimeError, "success"])
    retry_operation(fn)
    assert fn.call_count == 3
```

### 2. VERIFY RED｜确认失败（不可跳过）

跑单个测试，确认：

- 是「失败」不是「报错」；失败信息符合预期；
- 是因为功能缺失才失败，不是因为拼写错。

**测试直接通过？** 你在测已存在的行为，改测试。**测试报错？** 修到它能干净地「失败」为止。

### 3. GREEN｜最小实现

写让测试通过的**最少**代码。

```python
# 好：刚好够通过
def retry_operation(fn):
    for i in range(3):
        try:
            return fn()
        except RuntimeError:
            if i == 2:
                raise

# 坏：过度设计，加了测试没要求的东西
def retry_operation(fn, *, max_retries=3, backoff="linear", on_retry=None):
    ...
```

不要加新功能、不顺手重构别的代码、不做「超出测试的改进」。

### 4. VERIFY GREEN｜确认通过（不可跳过）

跑测试，确认：单个测试通过、其它测试仍通过、输出干净（无报错 / 警告）。

**测试没过？** 改代码，别改测试。**别的测试被带坏？** 现在就修。

### 5. REFACTOR｜清理

只在全绿之后：去重复、改名字、抽辅助函数。保持测试全绿，不加新行为。

然后写下一个失败测试，进入下一轮。

## 好测试 vs 坏测试

| 维度 | 好 | 坏 |
| --- | --- | --- |
| 最小 | 一次一件事；测试名含「and」就拆 | `test_validates_email_and_domain_and_whitespace` |
| 清晰 | 名字描述行为 | `test1` |
| 表达意图 | 演示你想要的 API | 让你看不出代码该长啥样 |

## 常见借口

| 借口 | 现实 |
| --- | --- |
| 「这个太简单不值得测」 | 简单代码照样坏。测它只要 30 秒，修复却可能半天。 |
| 「我先写实现再补测试」 | 那你根本没走 TDD，补的测试只会证明现有代码按现有写法对。 |
| 「mock 一下就行」 | mock 只证明「mock 被按预期调用」，不证明行为正确。 |
| 「测试太多拖慢进度」 | 没有测试的代码，后期改一行都怕。慢是因为没测，不是因为有测。 |
| 「这次先跳过」 | 每一次「这次」都会变成下一次。例外必须由用户给，不由自己给。 |

## 卡住时

| 问题 | 解法 |
| --- | --- |
| 不知道该测什么 | 先写你「想要」的 API，断言写出来；还不会就回去澄清需求。 |
| 测试太复杂 | 设计太复杂，简化接口。 |
| 全都要 mock | 代码耦合过紧，引入依赖注入。 |
| 测试准备代码巨大 | 抽测试辅助；还复杂就说明设计要简化。 |

## bug 修复与回归

发现 bug：先写一个能复现它的失败测试，再走红绿循环。测试既证明修复，也防回归。**没有测试不修 bug。**

## 收尾清单

离开前逐条勾：

- [ ] 每个新函数 / 方法都有测试
- [ ] 亲眼看过每个测试失败
- [ ] 失败原因是「功能缺失」，不是拼写错
- [ ] 用最少代码让每个测试通过
- [ ] 全部测试通过、输出干净
- [ ] 测试用真实代码（mock 只在迫不得已时）
- [ ] 边界与错误分支已覆盖

勾不全 = 跳过了 TDD，回炉重做。
