# 代码实现规范

把「一个说不清的需求」变成「一段说得清、可验证、能合入主干的代码」。目标不是把代码写完，而是写完时能拿出证据：这条代码**做对了**、**有测试兜底**、**主干仍可用**。

## 核心原则

1. 先想清楚再动手：需求没澄清、计划没写好，就还不该写码。
2. 铁律：先有失败的测试，才写生产代码（红绿重构）。没亲眼看过测试失败，就不知道它在测什么。
3. 最小实现：YAGNI，只写让测试通过的最少代码，不做测试没要求的「顺手优化」。
4. 无新鲜验证证据，不声称「完成 / 通过」。证据 = 这一节刚跑过、且输出确实证明该结论。
5. 遇 bug 先找根因再修：修前先 grep 该函数的所有调用方，在共享层修一次，而不是在每个调用方打补丁；不猜、不叠加补丁、不改症状。
6. 计划可被拷问：写完计划必须反问自己一遍，直到没有「想当然」的假设为止。
7. 实现只负责「把事做对」；做没做对交给 `code-review` 独立把关，不自己既当运动员又当裁判。
8. 先爬梯子再写码：写任何代码前，先问七层——有必要存在？仓库已有？标准库？平台原生？已装依赖？一行搞定？都不是才写。最好的代码是没写出来的代码。

## 先定场景

动手前先判断「这段代码的生命周期」，据此决定 TDD 强度：

- **throwaway（一次性脚本 / 原型 / 探索）**：不进长期维护。TDD 可放宽，但正确性验证不可省——至少要有能复现的运行方式与预期输出。底线是这段结果可信、不会误合并进主干。
- **maintained（新功能 / 缺陷修复 / 重构 / 行为变更，将进入主干）**：完整红绿重构。每个行为变更都有失败测试先行。

缺省判定：代码将合入主干、被他人依赖或需长期维护 → maintained；临时跑一遍就删、不提交 → throwaway。拿不准按 maintained，不向下放松。

### 强度档位（决定砍到什么程度）

| 档位 | 何时用 | 行为 |
| --- | --- | --- |
| **lite** | 探索 / 原型，只求跑通 | 给最简实现，顺带一句「更懒的替代方案」，你来选 |
| **full**（默认） | 维护代码、进主干 | 强制爬梯子 + 红绿重构，取最短可行 diff |
| **ultra** | 重构瘦身 / 删多于写 | 先删后写，挑战需求本身，能少写就少写 |

档位只影响「砍到什么程度」，不影响「必须验证」这条底线——lite 也要有可复现的运行方式与预期输出。

## 主流程

1. **澄清需求**：先确认「到底要做什么、验收标准是什么、明确不做哪些」。说不清就回到需求方问，不带着模糊需求写码（细则 `references/clarify.md`）。
2. **爬梯子**：对每条需求，先过一遍「是否真的需要写代码」的七层梯子，停在第一层能站稳的 rung；跳过不写的东西、用平台 / 标准库能覆盖的东西，一句话说清（细则 `references/ladder.md`）。
3. **写实现计划**：把需求拆成能独立验证的小任务——每个任务自带测试循环、值得单独提交；写清文件、接口、每步的代码与验证命令；写完自检（细则 `references/planning.md`）。
4. **红绿重构逐任务实现**：每任务走「写失败测试 → 确认失败 → 最小实现 → 确认通过 → 提交」（细则 `references/tdd.md`）。maintained 场景不可跳过。
5. **遇 bug 走四阶段调试**：根因调查 → 模式分析 → 假设与验证 → 修复并回归（细则 `references/debugging.md`）。
6. **交付前验证**：跑全量测试 / 构建 / lint 并读输出，逐条核对验收标准，才允许声称完成（细则 `references/verification.md`）。
7. **交收口**：自述变更范围与验证证据，把分支 / PR 交给 `code-review`，不自己批准自己。

## 输出要求

完成后简洁给出：① 需求与验收标准（澄清后的版本）；② 实现计划（任务清单）；③ 每个任务的红绿证据（失败原因 → 通过输出）；④ 全量验证命令与结果；⑤ 自检发现并修复的问题；⑥ 待 `code-review` 把关的点。不得把「没跑过」写成「已通过」。

## 红旗

- 没爬梯子就开始设计实现方案——跳过了七层检查，写出来的代码可能根本不需要存在。
- 需求没澄清就写码；或验收标准只有「能用」两个字。
- 只写实现不写计划；或计划里有 TODO、「适当处理异常」这类占位符。
- 先写生产代码、测试后补（maintained 场景）。
- 声称「测试应该能过」，但没实际跑过。
- 一次改多处，且不承诺每步可独立验证。
- 遇 bug 直接改：不复现、不找根因、一次试一堆修法。
- 自己写完立刻宣布「没问题」，不交给 `code-review`。
